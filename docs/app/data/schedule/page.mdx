# Schedule <span className="docs__label">Composition</span>

One row per item, drawn against a time axis, with today marked. A **timeline**, not a list: the point is
*which task runs which week*, *what overlaps*, and *what is late*.

## Grouped rows

Give an item a `parentId` and it becomes a child row, disclosed from its parent's name cell by a chevron
and an item count. Groups start collapsed; expansion survives fullscreen (pass `expanded` and
`onExpandedChange` to own it). Disclosure only decides which rows are shown: a parent's dates and
progress are the ones you gave it, never derived from its children.

<ScheduleGroupedDemo />

A child may state no dates (`{ id, label, parentId, unscheduled: true }`). It stays in its parent's group
and item count and is labelled, and no bar is drawn. A parent with only some children dated says its
coverage is partial. `onItemOpen` puts one labelled action on each top-level row. Use `itemHref` to make
that Details action a native link in both the grid and compact list; when it returns a destination,
`onItemOpen` is not called. If `itemHref` returns `undefined`, `onItemOpen` remains the callback fallback.
Children ignore `itemHref` and open through their own `onChildOpen` action, so they never repeat the
parent's destination or callback.

## What the bar says

The outlined bar is the plan: `start` to `end`, both **calendar days** (`YYYY-MM-DD`, inclusive — a
one-day item starts and ends on the same day). When `actual` is present, its `start` and `end` are
calendar days too, and a solid bar shows when the work actually ran. If the actual end is after the
planned end, that bar is marked as past the plan. Without `actual`, only the planned bar is drawn; its
fill shows `progress` (0–1), when reported. An item with no progress has no fill or percentage, because
absent is not done.

`today` decides what is **late**: an item whose end is behind it and whose progress is under 1. A
finished item is never late, however old. `weight` (basis points) is what makes a late item count for
more than a trivial one — the schedule draws it, and `lateWeightShare` reads it as a share of the plan.

## Where the drawing comes from

### Physical completion, not a reporting envelope

Use `mode="physical"` when progress reports establish completion rather than actual working dates.
The neutral contour keeps the inclusive planned range; blue fill measures reported completion inside
that contour. A fill boundary is **not** a date or forecast. `reportedOn` draws a separate diamond;
it does not create an actual start/finish range. An unknown progress reading uses a dashed contour
and “Not reported”, distinct from an explicitly reported 0%.

The aligned columns show actual/planned completion and their percentage-point gap. `latenessDays`
is a separate, caller-owned calendar reading: a physically complete item can have finished late.
Supply `onItemOpen` for a keyboard-accessible Details action and expose the facts behind the reading.
The name also has a full-text tooltip. Keep lifecycle completion separate from physical completion.

Physical mode supplies full-range, today and Day/Week/Month controls. Initial fit selects a readable
scale; a long range scrolls rather than squeezing its labels. Pass `view` and `onViewChange` to keep
scale and scroll offsets. Enable `fullscreen` to promote this same mounted schedule through the
browser's Fullscreen API. Where unavailable or denied, the explicit “Expand view” fallback fills
the window, isolates outside controls, and restores focus on return. Neither mode creates a dialog.
The exit action and Escape return to the inline view without losing scale, position or row controls.
Pass `toolbar` and `footer` so controls and the legend remain inside the fullscreen root. Tooltips
and menus resolve their popup container there. Render item details through `children` and use the
detail component's inline-container API (for example `Modal getContainer={false}`); body-mounted
portals otherwise sit behind the browser's fullscreen top layer. `Schedule.Skeleton` reserves the
chart height while its data is loading. The caller supplies a legend for its graphical meanings.

The grid and the bars are [SVAR React Gantt](https://svar.dev/react/gantt/) (`@svar-ui/react-gantt`,
MIT), bundled into `styles.css` the way React Flow is for `Diagram`. Its `--wx-*` custom properties are
pointed at Tokens in `schedule.css`, so a Skin or a theme moves the schedule with everything else and a
consumer never imports the substrate's CSS.

### What the free edition does not do

The substrate's `markers` API is a PRO feature: the free build ignores it. Schedule instead places a
token-coloured today line over the chart using the substrate's time scale, while also naming today
above the axis for readers and assistive technology. Lateness is this library's own reading too, from
`start`/`end`/`progress`, rather than the substrate's critical path, which is also PRO.

The visible date above the axis is formatted for a reader; its `<time dateTime>` preserves the original
calendar day. Pass `labels.todayDate` to write that date in the product's language.

## Responsive layout

The schedule measures its own container, not just the viewport. Below 680px (760px in physical mode) of available width it
gives the timeline the full panel and lists Work Item names and their actual percentages immediately below it; wider panels show
the names and an aligned Actual column beside the timeline. Missing progress reads “Not reported”,
which is distinct from a reported 0%. Resizing the panel or browser updates the mode without losing the
time axis. The narrow view includes a pan hint because later dates extend beyond the visible range.

## Tokens

Surfaces `--cb-surface` / `--cb-bg-subtle`, borders `--cb-border`, text `--cb-fg` and `--cb-fg-muted`,
`--cb-tone-brand` for a bar, `--cb-tone-danger` for a late one, `--cb-tone-warning` for the today
marker, and `--cb-radius-*` / `--cb-text-*` throughout.

# Board <span className="docs__label">Composition</span>

Columns of cards a person moves between states. A board's defining affordance is **movement**, so this
one moves by pointer **and** by keyboard — a column view where a card only moves through a dialog is
not a board.

## One path for both hands

Drag and keyboard reach the same answer because both call `onMove` with the same `BoardMove`, and the
rules that decide where a card lands are pure functions the board shares between them. Pointer dragging
is `@dnd-kit`'s; the keyboard path is the board's own, because two of its rules are the board's and not
a generic list's: a column that `accepts={false}` is **stepped over** rather than offered, and a card
crossing columns **keeps its depth** where the new column is long enough to hold it.

| Key | What it does |
|---|---|
| <kbd>Space</kbd> / <kbd>Enter</kbd> | Pick the card up, then drop it |
| <kbd>←</kbd> <kbd>→</kbd> | Move it between columns |
| <kbd>↑</kbd> <kbd>↓</kbd> | Move it within a column |
| <kbd>Esc</kbd> | Put it back |

Every step is announced in a polite live region: the pick-up, each landing place, the drop by the
card's own name, and any refusal.

## Cards that carry their own buttons need `handle`

A card is normally grabbed anywhere, which is right for a simple card. The moment a card carries its
own controls — Edit, Open, anything — set `handle`.

The reason is not taste. A whole-card grab makes the card itself a control, and a control has
**presentational children**: everything interactive inside it leaves the accessibility tree. Without a
handle, a card reading “Pour the slab · Open” exposes *one* control whose name is the whole card, and
the Open button cannot be reached at all. With `handle`, the card is plain markup, its buttons stay
reachable, and the handle is the one thing that drags and takes the keyboard.

<Guidance
  do="Set handle as soon as a card has a button inside it — the buttons stay reachable and the keyboard path moves to the handle."
  dont="Leave the whole card grabbable and put controls inside it; those controls disappear from the accessibility tree."
/>

## A refused move goes back

<BoardRefusalDemo />

The board applies a move optimistically so a card does not lag behind the hand that moved it, then asks
the consumer. Return `{ refused }` — or reject — and the board restores what was there and announces
why. An accepted move leaves an **Undo**, which is an ordinary move back through the same callback.

## On a phone

`layout="auto"` switches to **lanes** on a narrow viewport: one column at a time behind a lane
switcher, which is a deliberate rendering rather than a board squeezed until its columns are unusable.
Force it with `layout="lanes"` to see it, or `layout="board"` to keep the columns.

A card title clamps to two lines, so one long name cannot stretch its own card or the cards beside it.
Wrap the title in a tooltip when the full name matters.

## Loading

`Board.Skeleton` renders the same column and card geometry, so the page keeps its shape while the work
arrives.

## Tokens

Spacing `--cb-space-*`, radii `--cb-radius-*`, `--cb-shadow-sm|md|lg` for the rest, hover and carried
card, `--cb-tone-brand` for the drop marker and the held card, `--cb-tone-warning` for a column over
its limit, and `--cb-control-floor` so the lane switcher and Undo stay touch-sized.
